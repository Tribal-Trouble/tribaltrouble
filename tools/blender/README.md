# Tribal Trouble Blender Plugin

Official Blender import/export addon for Tribal Trouble geometry. Maintained in this repo; the game and the plugin version together.

## Install

1. Copy the `tools/blender/io_tribaltrouble` folder into Blender's add-ons folder. On Windows, from the repo root in PowerShell (put your Blender version in the path):
   `Copy-Item -Recurse tools\blender\io_tribaltrouble "$env:APPDATA\Blender Foundation\Blender\5.2\scripts\addons\"`
2. Start Blender and enable "Tribal Trouble Mesh (.xml)" in Edit > Preferences > Add-ons.

**Coming from 1.x** (the add-on used to be one file, `io_tribaltrouble.py`): its Update button cannot install 2.0, so switch once by hand. Close Blender, then from the repo root:

```
Remove-Item "$env:APPDATA\Blender Foundation\Blender\5.2\scripts\addons\io_tribaltrouble.py"
Copy-Item -Recurse tools\blender\io_tribaltrouble "$env:APPDATA\Blender Foundation\Blender\5.2\scripts\addons\"
```

Start Blender. The add-on keeps its name, so it is still enabled and still knows your repo folder. Do not use Remove in the Add-ons list for this: that forgets the repo folder.

## Use

- **Import**: File > Import > Tribal Trouble Mesh (.xml). Point it at any mesh under `assets/geometry/`; shift-select several files to import them all at once, one object each. UVs, vertex colors, and bone weights (as vertex groups) come along. When importing from inside the repo, the matching atlas PNG from `assets/textures/models/` is found automatically and a material is built for it ("Load Textures" option, on by default). If a texture appears vertically flipped, re-import with "Flip V" checked.
- **Export**: File > Export > Tribal Trouble Mesh (.xml). Exports every selected mesh object, merged in world space into one mesh (the scene is untouched), triangulated, with corner normals written as they are in Blender (imported normals survive as custom split normals). Skinning comes from bone-named vertex groups when the object has them (an imported unit round-trips with its weights), otherwise every vertex goes to `dummy_bone` (the static-prop convention used by plants and rocks). Meshes bound to an armature are exported in the rest pose whatever frame is showing. Object positions matter: what you see relative to the world origin is what the game gets. Set the texture atlas name in the export options or a `tt_texture` custom property on an object; comma-separated atlas lists pass through untouched.
- **Split Mesh by Bone** (Object menu): moves the faces weighted to one or more bones (comma separated, e.g. `Prop1, Prop2, Prop3`) into a new object, keeping UVs, normals, every vertex's weights and materials, so the part bends exactly as before. The rule "Mostly this bone" moves a face when every corner carries at least Min Weight on the bones; "Touches these bones" (the default for several bones) moves a face when any corner has any weight on them, so an item blended over several bones, like the viking chieftain's horn, comes out whole. The part is named after the first bone unless a Name is given. This is how a held item baked into a unit mesh (the warrior's axe on `Prop1`) becomes a separate attachment file. On a unit loaded from the Models list, add the new part with **New Prop...**, then **Publish** saves both the item and the trimmed unit mesh; split the Low detail mesh too if the item is baked into that one as well. For kits of separate parts (a unit plus its held items), check "One File Per Object" to write each selected object to its own `<object name>.xml` instead of merging.
- **Attachments**: to export a hat or held item that follows a unit bone, set "Attach To" in the export dialog (head, back, hands, prop bones, belt) and pick the unit skeleton; every vertex is skinned to that bone with weight 1. "Custom bone" takes an exact bone name. A `tt_bone` custom property on an object overrides the dialog, so a mixed selection can carry per-object bones even when merged. Model attachments in the unit's bind pose: import the unit mesh and place the item on it where it should sit. To place an item on a unit, load the unit from the Models panel and use **New Prop...** in the Props panel, which snaps it on. See `docs/blender-plugin/attachments.md` for the game side.

- **Skeletons and animations**: File > Import > Tribal Trouble Skeleton / Animation. Select a `*_skeleton.xml` and any clip files (`peon_run.xml`, `peon_idle.xml`, ...) together; the skeleton becomes an armature whose rest pose is exactly the file's, and each clip becomes an action keyed at frames 1..n. Meshes selected at import time whose vertex groups match the bones are parented with an Armature modifier, so importing `peon_mesh.xml` first and then the skeleton with the peon selected gives a rigged, animated unit. Clips alone can be imported onto the active armature later. File > Export > Tribal Trouble Skeleton / Animation writes the active armature's rest pose and every imported action back out, sampled at whole frames, each clip under the file name it was imported from. Clip type and speed (loop or plain, cycles per world unit) live in `geometry.xml`, not in the clip files.
- **Models panel** (sidebar N panel, "Tribal Trouble" tab, always the first panel there; the others follow in the order Skins, Preview, Props. Every kind of model gets the same panels; one hides only when it has nothing to offer, so Preview shows only for models with clips): set **Repo** once to your tribaltrouble checkout; it is remembered in the add-on preferences, and the first import through the file picker fills it in for you. The **Category** list above it picks what is listed: Units (anything with a skeleton), Buildings (with their `_halfbuilt` and `_start` stages), Resources (rocks, wood piles, treasure), Trees and Plants, Decorations (map scenery with `decoration=`), Other, or All. Clicking a model replaces the previously browsed one with its mesh, skeleton, every clip as an action (idle showing), and every attachment the registry declares for it. A model or item the registry lists with a second `<model>` (the low detail mesh the game draws from far away) loads that one too, hidden, named `<object>_lod1`. Objects you made yourself are never removed. **Publish** under Load is the one place to save: it writes everything you changed on the loaded model, any category (units, buildings, rocks, trees, props), back to the repo without asking anything: every detail level, items and props (new ones are listed in `geometry.xml` with the Event and On by default their New Prop form picked), clips and painted textures, each only when it changed since loading or the last Publish, so untouched files stay as they are. On a unit the check button next to it runs the checks, and the problems they find (or Publish refuses on) are listed under it. The bin next to it takes the loaded model out of the registry (see Remove From Registry). For a model that is not a unit, **Detail** (High / Low) sits under Publish when it has a far away mesh. Right click a row of the list for **Add To Scene: <model>**, which puts that row's model (not the loaded one) beside everything on screen, to its right with a small gap, at true game scale, units in their idle pose. Added models stay when you load another model, several sit side by side, and you can select and move them to compose a scene, but no Publish, export, items list, prop list or mesh picker ever takes them. **Remove Added Objects**, in the same menu and under the list while any are added, deletes them all, with their data; deleting one by hand with Delete works too.
- **Registry attachments**: a loaded unit lists its registry items per game slot (`hat`, `weapon`) in the Attachments panel. Click one to show it and hide the others in that slot, click it again for a bare unit. Default-on items such as the axe start visible.
- **Export Visible To Repo** writes registry items back to their own files and new items next to the unit as `<object name>.xml`, always in the rest pose, with no file picker. A registry item that has not changed since it was loaded is not written again, so files you did not touch stay as they are in the repo. The unit's own mesh at every detail level, and the low detail mesh of a shown item, are written the same way: only when changed, skinned with their bone weights, in the rest pose, with the texture list they loaded with. The report names the unit mesh files it wrote. So after cutting a baked-in weapon out of the body, Publish saves the body too. A new item whose file name is already taken in the unit's folder is refused instead of overwriting it. Each item's texture goes with it: the image in its material is written to `assets/textures/models/<image name>.png` when the repo lacks it or the image has unsaved paint, so a texture painted inside Blender needs no separate save. The mesh and the registry entry name the texture after that image. **Add To Registry** appends the matching sprite entries to the unit's group in `geometry.xml` and skips names already there. After that the item shows up in this browser and, after a build, in game.
- **New Model...** (Models panel, the full width button at the bottom) opens a form whose **Mesh** picker offers only your own meshes (the active mesh is filled in when it is one of them, and the Name follows the mesh picked); it exports that mesh, not whatever is active, as a brand new model into its own folder under `assets/geometry/<group>/<name>/` and appends its sprite entry to `geometry.xml`. With **Scatter on map** off it picks the kind from what the mesh is bound to: no armature gives a static building or model (with optional building stages, see below); an armature loaded from a registry unit gives a new unit on that rig (`base=`, skeleton and clips inherited); an armature the registry has never seen gives a unit with its own skeleton file and one clip per action (attack, die and throw clips are written as `plain`, the rest as `loop`, all with `wpc="1"` for a programmer to tune). Low Detail optionally names a second mesh for distance. The material's PNG is copied into `assets/textures/models` when the repo lacks it, and `team=` is written only when the decal exists in `assets/textures/teamdecals`. The model is browsable at once and converts with the game build; using it in game still needs code, and the report line gives the `/geometry/<group>/<name>.binsprite` path to reference there.
- **Scatter on map** in the New Model form makes map scenery the game scatters over every map by itself, such as Halloween pumpkin patches; no code is needed. Ticked, the form swaps the model fields for the **Terrain** (grass, dirt, beach: sand on native maps and gravel on viking maps, snow: viking maps only, or any land), the **Count** per map (default 20, at most 1000) and the **Event** (see Event dropdown below; All year writes none). OK writes the mesh to `assets/geometry/misc/<name>/<name>.xml`, copies its texture like any new model and appends `<sprite name="<name>" decoration="<terrain>" count="<N>" event="<event>">` to the `misc` group. Decorations are listed under the Decorations category, where each row loads it (show), paints it or removes it like any other model.
- **Preview panel** (with a unit loaded): one button per clip, which shows it and fits the timeline, plus Play. A button per tier (rock, iron, rubber) swaps the texture on the unit and on every attachment that has one texture per tier. **Detail** (High / Low, only when the model has a low detail mesh) shows the close up meshes or the far away ones, on the unit and its items alike; edit either and Publish saves each to its own file. **Team Color** blends the chosen color in through the team decal exactly as the game's sprite shader does, `mix(base, team, decal)`; it only shows in Material Preview shading, and the panel offers the switch.
- **Check Before Export** lists what breaks in game rather than in Blender: no UV map or a collapsed one, UVs outside 0 to 1, no Image Texture, a texture that is not a square power of two, object or image names that are not letters, digits and underscores, vertex colors that are not white (they tint the texture), vertices with no bone weight, and an item heavier than the unit. Errors stop Publish, Export Visible To Repo and New Model; warnings do not.
- Buttons that change `geometry.xml` for a unit (Publish, Add To Registry, and Delete Clip for a saved clip) only work on a unit loaded from the repo folder set in the Models panel, so they never edit a different checkout's registry.
- **Remove From Registry** (the bin next to Publish, on a registry item or a prop, or under a picked skin) cuts the sprite entry out of `geometry.xml` after a confirmation. The files stay on disk, and a removed skin that was on show gives way to the default look. It is refused while another sprite is based on it.
- **Building stages**: for a static model, New Model also takes optional Half Built and Start meshes (each with its own optional low detail mesh) and registers `<name>`, `<name>_halfbuilt` and `<name>_start` in one go, the way the existing buildings are laid out.
- **Updating**: when the copy of the add-on in your repo folder is newer than the installed one, the Models panel shows **Update add-on to x.y.z**. It copies the add-on's files over the installed ones, deletes a 1.x `io_tribaltrouble.py` still sitting next to them, and reloads. So after the first install, updating is: pull, press the button.
- **Installing as an extension** (Blender 4.2 and newer): `python tools/blender/build_extension.py` writes `tools/blender/dist/tribal_trouble_io-<version>.zip`; drag it into Blender. The `io_tribaltrouble` folder stays the single source, the zip is its modules plus a manifest. Do not install it both ways at once.
- **Props** (the panel that used to be called Carried Items, and Items On This Unit and Attachments before that): on a unit, an item is a separate mesh that follows one of the unit's bones, such as a hat, a weapon or something it carries. The top of the panel is one scrolling list of the items the unit already has. It grows with its rows up to 12 and scrolls after that; typing in the search field above it finds an item by name or by slot (`weapon`, `hat`, `carried`). A row shows the eye (show or hide the item), its name, its slot, a brush (Paint It) and a bin (Remove From Registry; carried items have none). An item the game only shows in some clips, such as the chieftain's magic prop, gets a clock button while another clip is playing: its tooltip lists the clips it appears in and clicking it shows the first one. Clicking a row opens that item in place of the list (it also becomes the active object; nothing is loaded or changed): **Back to items** at the top, then its row as in the list (eye, name, slot, brush and bin), **Give It Its Own Texture** when it applies, the clock hint when the clip showing hides it, and the item's **Skins** (see the Skins panel below). Loading another model, or the item going away, shows the list again. An item whose file weights several bones, such as the viking chieftain's lur, deforms with all of them the way the unit does, Publish writes its weights back, and it counts as showing in a clip when any of its bones shows. Items on the chicken go in `slot="prop"`, since the game treats it as scenery; its head and back are attachment points. **New Prop...** opens a small form: **Where** (head, back, a hand...), **Mesh** (only your own meshes are offered; a selected one is filled in), **Snap to <point>** (on by default), **Event** (see Event dropdown below; written as `event=`), **On by default** (`default="true"`, so every unit wears it, like a pumpkin hat for everyone at Halloween) and, when the mesh has no image yet, **Make a texture for it** (on by default). OK hangs the mesh on that bone straight away so you can press Play and judge it. Each item added this way gets a small box under the list with **Snap again**, **Paint It** (or Make A Texture For It); the picker in it swaps or clears the mesh. **Publish** in the Models panel runs the checks, writes every visible item and its texture into the unit's folder, and lists the new ones in `geometry.xml` with what their New Prop form picked. Items already in the registry keep their attributes. One mesh is one item; nothing is merged. A saved item becomes one of the unit's buttons, and its file in the repo is the real copy from then on. The separate steps (export only, add to registry only, copy a snippet) are under **By hand**, closed by default.
- **Snap to head** (or back, right hand...) in the New Prop form, and **Snap again** afterwards, moves your mesh onto the unit. On the head it sits on the crown of the skull, under any horns or feathers; elsewhere its origin goes to the joint, so model a held item with its grip at the origin. A mesh bigger than the whole unit is shrunk to 30% of the unit's height first, and the checks warn about oversized items. Nudge it afterwards as you like.
- **Paint It** (in a new item's box, and in an open item) selects the mesh, makes its image the canvas and opens Texture Paint. When that workspace has no Image Editor (or there is no Texture Paint workspace, in which case it stays on the current one), it splits the largest 3D view and shows the image on the left, once; later presses reuse it. **Done Painting** brings you back to the unit.
- **Make A Texture For It** is a checkbox in the New Prop form, a red button in a new item's box when your mesh has no image texture. One click unwraps the mesh if it has no UV map, makes a material with one image named after the mesh, filled with the color the material had, and tidies the mesh name into letters, digits and underscores. When another texture already has that name, the image gets `_2`, `_3` and so on, so it never paints over another model's texture. Paint it in the Texture Paint tab; Publish writes the PNG. Only that base color image reaches the game: its model shader draws texture times vertex color times light, plus the team decal. There is a normal map slot in the shader, but today only the built-in generated textures (the rock and iron lumps) fill it; textures loaded from files are color only. Roughness, metal and node setups have nothing to map to.
- **Give It Its Own Texture** (in an open item, and under the Mesh picker) shows when an item is still drawn from its unit's texture, as items split out of a unit are: the warrior's axe uses the warrior's rock, iron and rubber atlases. It copies the part of each atlas the item's UVs cover (every detail level, a few pixels of margin) into a square power of two image at the same pixel size, nothing resampled, the leftover area filled by repeating the edge pixels, and does the same for each team decal. One texture is named after the item; one per tier gives `<item>_rock`, `<item>_iron`, `<item>_rubber`. The UVs move onto the new images so every point shows the same pixel as before, and Show Tier swaps the item to its own tier image. Publish writes the PNGs into `assets/textures/models` and `assets/textures/teamdecals` and changes only that item's texture lines in `geometry.xml`; the unit and its atlas are not touched. A name already taken by an image or a PNG is refused, and nothing changes.
- **Clips**: **New Clip** in the Preview panel starts a clip from the pose on screen, keyed on the first and last frame only, which is the easy way to animate by hand (game clips carry a key on every frame for every bone). It can also start from a full copy of the clip showing, for small fixes. Its form also asks whether it plays looping or once and, for a walk or run, the distance travelled per loop. **Publish** writes every new clip and every clip whose keys you changed into the unit's folder and adds or updates its `<animation>` line; an existing clip keeps how it plays. Saving over an existing clip (a better run, a new death) needs no code. A brand new clip must have a name no clip of the unit has and whose file is not already in the unit's folder. It is listed last so the clip numbers the game already uses do not move; items and carried things inherit it from the unit. The game plays it only once code asks for it. A unit that borrows another unit's rig cannot change the clips: load the rig's own unit. **Delete Clip** (the bin, or right click a clip button) drops a clip you never saved; for a saved one it also removes the registry lines and the file, and only the last clip in the list can go, because removing an earlier one would shift the numbers after it.
- The point rows in the Attachments panel only take your own new meshes. Items that came from the registry have their own buttons above. Clearing a row lets your mesh go without deleting it.
- **Carried items**: wood, rock (iron is its second texture), rubber and the two paddles are registry items on the peon in the `carried` slot. They load with their peon in a **Carried** box: click one to see it on the body, edit it, and Publish writes it back to its own file. The game, not the player, decides which one shows, from what the peon is hauling or whether it is rowing. They cannot be removed from the registry because the game asks for these five by name. During an event, a carried sprite named `<name>_<event>` (for example `wood_resource_christmas` with `event="christmas"`) stands in for `<name>`, and an event skin on the item works too.
- **Props on buildings and scenery**: with a building, tree, rock, plant, treasure, decoration or other model loaded, the Props panel lists its props the same way it lists a unit's items, even when it has none yet: search field, one row per prop (eye, name, a tag, brush, bin) and, on a click, the prop on its own with **Back to items**, Paint It, Remove From Registry and its Skins. The tag of a building prop is its stage (Built, Half built or Start) and its event (or All year); other props show the event. Props are meshes placed around the model and drawn with it; they load with it and are written back to their own files. **New Prop...** under the list opens a form: **Mesh** (only your own meshes are offered; a selected one is filled in), on a building **Attaches to** (the building and the stage showing, read only), on a tree **Sits on** (its trunk or its crown, when the registry has both), **Event** (see Event dropdown below) and, when the mesh has no image yet, **Make a texture for it**. OK writes the mesh into the model's folder, in place as you arranged it, registers it with `base=` the stage or sprite it sits on and `slot="prop"`, and writes back the props already listed and the model's own meshes like Publish. After that, **Publish** in the Models panel writes the prop when you change it. A new prop whose sprite or file name is already taken is refused. To see an event in game, start it with `-Dcom.oddlabs.tt.event=<event>`.
- **Event dropdown**: every form that asks for an event (New Prop on units, buildings and scenery, New Skin, New Model with Scatter on map) offers the same list: **All year** (no event) where the event is optional, every event `geometry.xml` already names, and every event made this session. For a skin, All year means players who own it; New Skin on a model nobody owns (anything in the `misc` group: trees, rocks, the chicken, decorations) has no All year and needs an event. The **+** next to it opens a small **New Event** form with a **Name** (letters, digits and underscores; it is lowercased); its OK brings the form back with everything you had filled in and the new event picked. A new event reaches `geometry.xml` only once something published uses it.
- **Forms**: the OK button of a form stays greyed out until the form can be used, for example until a Mesh is picked or a name uses only letters, digits and underscores.
- **Skins panel** (right under Models, with any model loaded from the Models list): a skin is another look for a model. Without an event, a player who owns it sees it on every one of these models; with an event, everyone sees it while that event is on (see "Skins" in `docs/blender-plugin/attachments.md`). Owned skins are for units and buildings of the tribes; anything nobody owns only takes event skins. The panel is a list like the Props list: **Default** and the skins `geometry.xml` already has for the loaded model, one row each with the eye, its name, a greyed tag saying who gets it (**Owned** or the event's name), a brush and, for a skin, a bin. The eye shows that skin on every detail level (Default shows the model's own files again; unsaved edits are dropped; the eye of the skin showing goes back to Default), and the highlighted row is always the look on screen. The brush shows that look and opens Texture Paint on its texture; the bin takes a skin out of the registry after a confirmation, its files staying on disk. Paint on a skin's own texture is written by Publish; a skin that uses the default texture there refuses the brush, so the default texture is never painted this way; make a New Skin with its own texture instead. To make one, press **New Skin...** and give it a name (letters, digits, underscores; the field offers skin names `geometry.xml` already uses anywhere), optionally a **Mesh** of your own as its shape (the loaded model hides while you work) and the **Event**. A banner then reads **Editing skin '<name>' for <model>**: change the loaded model (reshape the mesh, paint its texture or give it another image) and press **Save Skin**, or **Cancel** to show the default look again with your edits dropped and nothing written. Starting a skin while previewing another shows Default first. Preview, Default, Save Skin and Cancel leave Texture Paint first, since it draws the paint canvas rather than the model's material, so the swap shows at once. One skin name covers many models: save the same name on the peon, the warrior and the quarters and a player who owns it sees all three. It appends `<model>_<skin>` with `skin=` and `replaces=` (and `base=` for a unit, so it keeps the clips, and `event=` for an event skin) to the model's group. A detail level whose mesh you did not change keeps pointing at the default file, so a new texture alone makes a texture-only skin; a changed one is written next to the default file as `<model>_<skin>.xml` (`<model>_<skin>_lo.xml` for the far away mesh), skinned like Publish does. Only the tier on screen takes the new image; the other tiers keep theirs. Paint on the default texture itself is saved as `<texture>_<skin>.png`. A new texture keeps the default tier's team decal unless it has its own. A building stage (`_halfbuilt`, `_start`) is a skin of its own. A skin name the loaded model already has, a taken sprite name, a file already on disk or no change from the default model is refused. The default files and registry entry are never written, and the model shows its default look again afterwards, so Publish does not save the skin over it; Publish also skips a model while it previews a skin, and an item while a skin is being made for it.
- **Item skins**: an open item or prop in the Props panel has its own **Skins** box: the same list, with **Default** and one row per skin that covers it, each with the eye, brush and bin as in the Skins panel, and **New Skin...**. The form asks for the skin name as above and an optional **Mesh**. Left blank, you repaint or reshape the item itself under the **Editing skin '<name>' for <item>** banner, as for a model. With one of your own meshes picked, that mesh becomes the skin's shape: it is hung on the item's bone (**Snap to <point>**, on by default), the default item hides while you work, and **Make a texture for it** is offered when the mesh has no image. **Save Skin** appends `<item>_<skin>` with the item's `base=` and `slot=` plus `skin=` and `replaces=`. A changed item mesh is written as `<item>_<skin>.xml` (and `_lo`); your own mesh is written as `<item>_<skin>.xml` alone, and your mesh comes off the unit and hides. A new texture for an item skin is named with the race, like the item's own textures: `viking_peon_hammer_gold` (with the tier, `viking_warrior_axe_held_rock_gold`, when the item has tiers). The item's files, textures and registry entry are never written; **Cancel** takes your mesh back off and shows the default item. The Skins panel lists only the loaded model's own skins; one that also covers loaded items reads like `gold (+ peon_hammer)`, and its preview swaps all of them. A skin that covers only items shows only in those items' views.
- **Tests**: `blender -b --factory-startup --python tools/blender/tests/test_addon.py` runs the whole add-on headless against a temporary copy of `assets/geometry` and never writes to the repo. Run it, and `validate_roundtrip.py`, before committing a change to the add-on.
- **By hand** (under Props on a unit, closed by default): **Refresh Points** makes one slot per attachment point the skeleton has bones for; New Prop puts your mesh in one, bone-parented at its current placement (relative to the bone as posed at that moment, so it is safe to assign while scrubbing), tagged with `tt_bone`, following the bone through every clip. **Export Visible To Repo** and **Add To Registry** are the two halves of what Publish does for items. **Export Visible Attachments** writes one file per new item skinned to its bone, always in the rest pose. **Copy Registry Snippet** puts matching `geometry.xml` entries on the clipboard, using the `base=` shorthand that inherits the unit's skeleton and clips. Each entry carries a `slot=` (head gives `hat`, Prop1 gives `weapon`, other points use their own name). The game wires units from these entries at build time, so a new item needs no Java: paste the entry, put the texture in `assets/textures/models`, rebuild. Several items can share a slot; in game, with cheats on (`/iamacheater` in chat), H cycles the `hat` slot on the selected units. Add `default="true"` to an entry to have units start with it.

## Code layout

The add-on is the package `tools/blender/io_tribaltrouble/`. Lower modules never import higher ones, in this order:

- `textures.py`: materials, team color nodes, texture files and atlas crops.
- `mesh_io.py`: mesh XML read and write, and the Blender meshes built from it.
- `rig.py`: skeleton and clip XML read and write, and the armatures, actions and attachment points built from them.
- `registry.py`: the repo folder and `geometry.xml`: reading it, adding and removing entries, sprite text, skins.
- `scene.py`: the models loaded in the scene: loading, which level and item shows, attachments on bones, added reference models, skin lookups.
- `publish.py`: writing changed models, items, clips and textures to the repo, and the checks run before that.
- `forms.py`: what the popup forms share: the OK row, reopening after New Event, the event dropdown and the events it offers, name and mesh checks.
- `import_export.py`: File > Import and File > Export operators, and Split Mesh by Bone.
- `models.py`: Models panel: the model list, Load, Publish, New Model, Check, Add To Scene, and the Update add-on button.
- `preview.py`: Preview panel: clips, tiers, material preview, New Clip, Delete Clip.
- `by_hand.py`: By hand panel: attachment points, registry snippets and exports done one step at a time.
- `skins.py`: Skins panel: showing, making, painting and saving skins.
- `props.py`: Props panel: the item and prop lists, an open item, New Prop, painting and own textures.
- `__init__.py`: `bl_info`, the list of classes, and register and unregister with the window manager properties.

## Validation

`tools/blender/validate_roundtrip.py` imports files, re-exports them, and diffs every value. Give it a skeleton plus clips, or one or more mesh files. Run it from the repo root after touching the import or export code:

```
blender -b --python tools/blender/validate_roundtrip.py -- assets/geometry/vikings/peon/peon_skeleton.xml assets/geometry/vikings/peon/peon_run.xml
blender -b --python tools/blender/validate_roundtrip.py -- assets/geometry/vikings/warrior/warrior_mesh.xml
```

Positions, UVs, weights and matrices come back within the files' own print precision. Normals compare by direction only (the source files carry normals of any length, the game normalises at load) and a few corners can differ by up to a degree, which is Blender's custom normal storage, not a bug. Zero-weight skin entries in the source files are dropped and duplicate bone entries for one vertex are summed; both match how the game reads them.

## Scope

Static props, rigid attachments, skinned units, skeleton and clip round trips, new models, items, props, skins and scattered decorations in `geometry.xml`. Not covered yet: normal maps. A new model other than an item, a prop, a skin or a scattered decoration still needs code (such as `RacesResources`) to be used in game.

## Format notes

- The game is Z-up like Blender; no axis conversion happens.
- Mesh XML: `mesh > polygons > polygon > vertex`, each vertex with position, normal, UV (optional second UV), RGBA vertex color, and one or more `skin` bone weights. Static meshes carry no `skeleton` section.
- Skeletons live in separate `*_skeleton.xml` files; animations in per-clip XMLs of per-frame, per-bone 4x4 matrices.
