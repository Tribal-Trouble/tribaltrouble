# Tribal Trouble Blender Plugin

Official Blender import/export addon for Tribal Trouble geometry. Maintained in this repo; the game and the plugin version together.

## Install

1. Blender 4.x: Edit > Preferences > Add-ons > Install...
2. Pick `io_tribaltrouble.py`, then enable "Tribal Trouble Mesh (.xml)".

## Use

- **Import**: File > Import > Tribal Trouble Mesh (.xml). Point it at any mesh under `assets/geometry/`; shift-select several files to import them all at once, one object each. UVs, vertex colors, and bone weights (as vertex groups) come along. When importing from inside the repo, the matching atlas PNG from `assets/textures/models/` is found automatically and a material is built for it ("Load Textures" option, on by default). If a texture appears vertically flipped, re-import with "Flip V" checked.
- **Export**: File > Export > Tribal Trouble Mesh (.xml). Exports every selected mesh object, merged in world space into one mesh (the scene is untouched), triangulated, with corner normals written as they are in Blender (imported normals survive as custom split normals). Skinning comes from bone-named vertex groups when the object has them (an imported unit round-trips with its weights), otherwise every vertex goes to `dummy_bone` (the static-prop convention used by plants and rocks). Meshes bound to an armature are exported in the rest pose whatever frame is showing. Object positions matter: what you see relative to the world origin is what the game gets. Set the texture atlas name in the export options or a `tt_texture` custom property on an object; comma-separated atlas lists pass through untouched.
- **Split Mesh by Bone** (Object menu): moves every face whose corners are all weighted to one bone into a new object, keeping UVs, normals, weights and materials. This is how a held item baked into a unit mesh (the warrior's axe on `Prop1`) becomes a separate attachment file. On a unit loaded from the Models list, pick the new part as the Mesh under **Add a new item**, then **Publish** saves both the item and the trimmed unit mesh; split the Low detail mesh too if the item is baked into that one as well. For kits of separate parts (a unit plus its held items), check "One File Per Object" to write each selected object to its own `<object name>.xml` instead of merging.
- **Attachments**: to export a hat or held item that follows a unit bone, set "Attach To" in the export dialog (head, back, hands, prop bones, belt) and pick the unit skeleton; every vertex is skinned to that bone with weight 1. "Custom bone" takes an exact bone name. A `tt_bone` custom property on an object overrides the dialog, so a mixed selection can carry per-object bones even when merged. Model attachments in the unit's bind pose: import the unit mesh and place the item on it where it should sit. To place an item on a unit, load the unit from the Models panel and use Snap To in Carried Items. See `docs/blender-plugin/attachments.md` for the game side.

- **Skeletons and animations**: File > Import > Tribal Trouble Skeleton / Animation. Select a `*_skeleton.xml` and any clip files (`peon_run.xml`, `peon_idle.xml`, ...) together; the skeleton becomes an armature whose rest pose is exactly the file's, and each clip becomes an action keyed at frames 1..n. Meshes selected at import time whose vertex groups match the bones are parented with an Armature modifier, so importing `peon_mesh.xml` first and then the skeleton with the peon selected gives a rigged, animated unit. Clips alone can be imported onto the active armature later. File > Export > Tribal Trouble Skeleton / Animation writes the active armature's rest pose and every imported action back out, sampled at whole frames, each clip under the file name it was imported from. Clip type and speed (loop or plain, cycles per world unit) live in `geometry.xml`, not in the clip files.
- **Models panel** (sidebar N panel, "Tribal Trouble" tab): set **Repo** once to your tribaltrouble checkout; it is remembered in the add-on preferences, and the first import through the file picker fills it in for you. The **Category** list above it picks what is listed: Units (anything with a skeleton), Buildings (with their `_halfbuilt` and `_start` stages), Resources (rocks, wood piles, treasure), Trees and Plants, Other, or All. Clicking a model replaces the previously browsed one with its mesh, skeleton, every clip as an action (idle showing), and every attachment the registry declares for it. A model or item the registry lists with a second `<model>` (the low detail mesh the game draws from far away) loads that one too, hidden, named `<object>_lod1`. Objects you made yourself are never removed. **Publish Loaded Model** under Load saves whatever you edited on the loaded model, any category (units, buildings, rocks, trees, props), back to its own files: every detail level, item and prop, each only when it changed since loading, so untouched files stay as they are.
- **Registry attachments**: a loaded unit lists its registry items per game slot (`hat`, `weapon`) in the Attachments panel. Click one to show it and hide the others in that slot, click it again for a bare unit. Default-on items such as the axe start visible.
- **Export Visible To Repo** writes registry items back to their own files and new items next to the unit as `<object name>.xml`, always in the rest pose, with no file picker. A registry item that has not changed since it was loaded is not written again, so files you did not touch stay as they are in the repo. The unit's own mesh at every detail level, and the low detail mesh of a shown item, are written the same way: only when changed, skinned with their bone weights, in the rest pose, with the texture list they loaded with. The report names the unit mesh files it wrote. So after cutting a baked-in weapon out of the body, Publish saves the body too. A new item whose file name is already taken in the unit's folder is refused instead of overwriting it. Each item's texture goes with it: the image in its material is written to `assets/textures/models/<image name>.png` when the repo lacks it or the image has unsaved paint, so a texture painted inside Blender needs no separate save. The mesh and the registry entry name the texture after that image. **Add To Registry** appends the matching sprite entries to the unit's group in `geometry.xml` and skips names already there. After that the item shows up in this browser and, after a build, in game.
- **Register New Model** (Models panel, with a mesh active) exports a brand new model into its own folder under `assets/geometry/<group>/<name>/` and appends its sprite entry to `geometry.xml`. It picks the kind from what the mesh is bound to: no armature gives a static building or prop; an armature loaded from a registry unit gives a new unit on that rig (`base=`, skeleton and clips inherited); an armature the registry has never seen gives a unit with its own skeleton file and one clip per action (attack, die and throw clips are written as `plain`, the rest as `loop`, all with `wpc="1"` for a programmer to tune). Low Detail optionally names a second mesh for distance. The material's PNG is copied into `assets/textures/models` when the repo lacks it, and `team=` is written only when the decal exists in `assets/textures/teamdecals`. The model is browsable at once and converts with the game build; using it in game still needs code, and the report line gives the `/geometry/<group>/<name>.binsprite` path to reference there.
- **Preview panel** (with a unit loaded): one button per clip, which shows it and fits the timeline, plus Play. A button per tier (rock, iron, rubber) swaps the texture on the unit and on every attachment that has one texture per tier. **Detail** (High / Low, only when the model has a low detail mesh) shows the close up meshes or the far away ones, on the unit and its items alike; edit either and Publish saves each to its own file. **Team Color** blends the chosen color in through the team decal exactly as the game's sprite shader does, `mix(base, team, decal)`; it only shows in Material Preview shading, and the panel offers the switch.
- **Check Before Export** lists what breaks in game rather than in Blender: no UV map or a collapsed one, UVs outside 0 to 1, no Image Texture, a texture that is not a square power of two, object or image names that are not letters, digits and underscores, vertex colors that are not white (they tint the texture), vertices with no bone weight, and an item heavier than the unit. Errors stop Export Visible To Repo and Register New Model; warnings do not.
- Buttons that change `geometry.xml` for a unit (Publish, Add To Registry, Publish Clip, and Delete Clip for a saved clip) only work on a unit loaded from the repo folder set in the Models panel, so they never edit a different checkout's registry.
- **Remove From Registry** (the bin next to a registry item, or next to Register New Model for the model picked in the list) cuts the sprite entry out of `geometry.xml` after a confirmation. The files stay on disk. It is refused while another sprite is based on it.
- **Building stages**: for a static model, Register New Model also takes optional Half Built and Start meshes (each with its own optional low detail mesh) and registers `<name>`, `<name>_halfbuilt` and `<name>_start` in one go, the way the existing buildings are laid out.
- **Updating**: when the copy of the add-on in your repo folder is newer than the installed one, the Models panel shows **Update add-on to x.y.z**. It copies the file over the installed one and reloads. So after the first install, updating is: pull, press the button.
- **Installing as an extension** (Blender 4.2 and newer): `python tools/blender/build_extension.py` writes `tools/blender/dist/tribal_trouble_io-<version>.zip`; drag it into Blender. `io_tribaltrouble.py` stays the single source, the zip is that file plus a manifest. Do not install it both ways at once.
- **Carried Items** (the panel that used to be called Items On This Unit, and Attachments before that): an item is a separate mesh that follows one of the unit's bones, such as a hat, a weapon or something it carries. The top of the panel is one scrolling list of the items the unit already has. It keeps its height whether there are 5 items or 500; the buttons above it narrow it to Hats, Weapons or Carried, and typing in the search field between those buttons and the list finds an item by name. The eye shows or hides an item and the bin removes it from the registry. **Add a new item** is two fields: **Where** (head, back, a hand...) and **Mesh**. Place your mesh on the unit, pick it, and it follows that bone straight away so you can press Play and judge it. **Publish** is the only button: it runs the checks, writes every visible item and its texture into the unit's folder, and lists the new ones in `geometry.xml`. One mesh is one item; nothing is merged. A saved item becomes one of the unit's buttons, and its file in the repo is the real copy from then on. The separate steps (export only, add to registry only, copy a snippet) are under **By hand**, closed by default.
- **Snap To Head** (or Back, Right Hand...) under the Mesh picker moves your mesh onto the unit. On the head it sits on the crown of the skull, under any horns or feathers; elsewhere its origin goes to the joint, so model a held item with its grip at the origin. A mesh bigger than the whole unit is shrunk to 30% of the unit's height first, and the checks warn about oversized items. Nudge it afterwards as you like.
- **Paint It** (under the Mesh picker, and the brush on every row of the items list) selects the mesh, makes its image the canvas and opens Texture Paint; **Done Painting** brings you back to the unit.
- **Make A Texture For It** appears in red under the Mesh picker (and per new prop in the Building panel) when your mesh has no image texture. One click unwraps the mesh if it has no UV map, makes a material with one image named after the mesh, filled with the color the material had, and tidies the mesh name into letters, digits and underscores. When another texture already has that name, the image gets `_2`, `_3` and so on, so it never paints over another model's texture. Paint it in the Texture Paint tab; Publish writes the PNG. Only that base color image reaches the game: its model shader draws texture times vertex color times light, plus the team decal. There is a normal map slot in the shader, but today only the built-in generated textures (the rock and iron lumps) fill it; textures loaded from files are color only. Roughness, metal and node setups have nothing to map to.
- **Give It Its Own Texture** (the picture button on an item's row, and under the Mesh picker) shows when an item is still drawn from its unit's texture, as items split out of a unit are: the warrior's axe uses the warrior's rock, iron and rubber atlases. It copies the part of each atlas the item's UVs cover (every detail level, a few pixels of margin) into a square power of two image at the same pixel size, nothing resampled, the leftover area filled by repeating the edge pixels, and does the same for each team decal. One texture is named after the item; one per tier gives `<item>_rock`, `<item>_iron`, `<item>_rubber`. The UVs move onto the new images so every point shows the same pixel as before, and Show Tier swaps the item to its own tier image. Publish writes the PNGs into `assets/textures/models` and `assets/textures/teamdecals` and changes only that item's texture lines in `geometry.xml`; the unit and its atlas are not touched. A name already taken by an image or a PNG is refused, and nothing changes.
- **Clips**: **New Clip** in the Preview panel starts a clip from the pose on screen, keyed on the first and last frame only, which is the easy way to animate by hand (game clips carry a key on every frame for every bone). It can also start from a full copy of the clip showing, for small fixes. **Publish Clip** writes the clip on screen into the unit's folder and adds or updates its `<animation>` line, with a choice of looping or once and, for a walk or run, the distance travelled per loop. Saving over an existing clip (a better run, a new death) needs no code. A brand new clip must have a name no clip of the unit has and whose file is not already in the unit's folder. It is listed last so the clip numbers the game already uses do not move; items and carried things inherit it from the unit. The game plays it only once code asks for it. A unit that borrows another unit's rig cannot change the clips: load the rig's own unit. **Delete Clip** (the bin, or right click a clip button) drops a clip you never saved; for a saved one it also removes the registry lines and the file, and only the last clip in the list can go, because removing an earlier one would shift the numbers after it.
- The point rows in the Attachments panel only take your own new meshes. Items that came from the registry have their own buttons above. Clearing a row lets your mesh go without deleting it.
- **Carried items**: wood, rock (iron is its second texture), rubber and the two paddles are registry items on the peon in the `carried` slot. They load with their peon in a **Carried** box: click one to see it on the body, edit it, and Publish writes it back to its own file. The game, not the player, decides which one shows, from what the peon is hauling or whether it is rowing. They have no bin button because the game asks for these five by name. During an event, a carried sprite named `<name>_<event>` (for example `wood_resource_christmas` with `event="christmas"`) stands in for `<name>`, and an event texture on the item works as it does on buildings.
- **Building panel** (with a building loaded; pick Buildings in the Category list to find them): **Event** names the season, blank meaning all year, otherwise letters, digits and underscores. **Detail** switches between the building's close up and far away mesh. **Publish Props** writes each selected mesh into the building's folder, in place around the building as you arranged it, and registers it on that building stage; props already in the registry are listed, load with the building, and are written back to their own files. The building's own meshes are written back too, each detail level only when it changed. A new prop whose file name is already taken in the building's folder is refused. **Start Event Texture** puts a copy of the building's atlas on it, named `<texture>_<event>`, so you paint the copy and never the original. **Publish Event Texture** writes it into the repo and lists it for the event on every model that shares the atlas (or only the one on screen). Models seen from far away keep their usual texture unless you also paint `<their texture>_<event>.png`. The small buttons switch between the usual and event textures. To see an event in game, start it with `-Dcom.oddlabs.tt.event=<event>`.
- **Skins panel** (with a unit or building loaded from the Models list): a skin is what a player who owns it sees on every one of these units or buildings (see "Player skins" in `docs/blender-plugin/attachments.md`). The panel lists the skins `geometry.xml` already has for the loaded model: click one to see it on every detail level, **Stock** to go back (unsaved edits are dropped), the bin to take it out of the registry after a confirmation, its files staying on disk. To make one, change the loaded model (reshape the mesh, paint its texture or give it another image), type a **Skin Name** (letters, digits, underscores) and press **Save As Skin**. It appends `<model>_<skin>` with `skin=` and `replaces=` (and `base=` for a unit, so it keeps the clips) to the model's group. A detail level whose mesh you did not change keeps pointing at the stock file, so a new texture alone makes a texture-only skin; a changed one is written next to the stock file as `<model>_<skin>.xml` (`<model>_<skin>_lo.xml` for the far away mesh), skinned like Publish does. Only the tier on screen takes the new image; the other tiers keep theirs. Paint on the stock texture itself is saved as `<texture>_<skin>.png`. A new texture keeps the stock tier's team decal unless it has its own. A building stage (`_halfbuilt`, `_start`) is a skin of its own. A taken name, a file already on disk or no change from stock is refused. The stock files and registry entry are never written, and the model shows its stock look again afterwards, so Publish Loaded Model does not save the skin over it; Publish also skips a model while it previews a skin.
- **Tests**: `blender -b --factory-startup --python tools/blender/tests/test_addon.py` runs the whole add-on headless against a temporary copy of `assets/geometry` and never writes to the repo. Run it, and `validate_roundtrip.py`, before committing a change to the add-on.
- **Attachments panel** (sidebar N panel, "Tribal Trouble" tab, with an armature or one of its meshes active): one slot per attachment point the skeleton has bones for. Pick a mesh in a slot and it is bone-parented at its current placement (relative to the bone as posed at that moment, so it is safe to assign while scrubbing), tagged with `tt_bone`, and follows the bone through every clip. The eye toggle hides it. "Export Visible Attachments" writes one file per visible attachment skinned to its bone, always in the rest pose. "Copy Registry Snippet" puts matching `geometry.xml` entries on the clipboard, using the `base=` shorthand that inherits the unit's skeleton and clips. Each entry carries a `slot=` (head gives `hat`, Prop1 gives `weapon`, other points use their own name). The game wires units from these entries at build time, so a new item needs no Java: paste the entry, put the texture in `assets/textures/models`, rebuild. Several items can share a slot; in game, with cheats on (`/iamacheater` in chat), H cycles the `hat` slot on the selected units. Add `default="true"` to an entry to have units start with it.

## Validation

`tools/blender/validate_roundtrip.py` imports files, re-exports them, and diffs every value. Give it a skeleton plus clips, or one or more mesh files. Run it from the repo root after touching the import or export code:

```
blender -b --python tools/blender/validate_roundtrip.py -- assets/geometry/vikings/peon/peon_skeleton.xml assets/geometry/vikings/peon/peon_run.xml
blender -b --python tools/blender/validate_roundtrip.py -- assets/geometry/vikings/warrior/warrior_mesh.xml
```

Positions, UVs, weights and matrices come back within the files' own print precision. Normals compare by direction only (the source files carry normals of any length, the game normalises at load) and a few corners can differ by up to a degree, which is Blender's custom normal storage, not a bug. Zero-weight skin entries in the source files are dropped and duplicate bone entries for one vertex are summed; both match how the game reads them.

## Scope

Static props, rigid attachments, skinned units, skeleton and clip round trips. Not covered yet: normal maps, and registering a new non-attachment model in `geometry.xml` and `RacesResources` still happens by hand. Attachments only need the registry snippet.

Getting a new model in game (registration is not automated yet): put the exported XML under `assets/geometry/`, add an entry to `geometry.xml`, and reference it from `RacesResources`.

## Format notes

- The game is Z-up like Blender; no axis conversion happens.
- Mesh XML: `mesh > polygons > polygon > vertex`, each vertex with position, normal, UV (optional second UV), RGBA vertex color, and one or more `skin` bone weights. Static meshes carry no `skeleton` section.
- Skeletons live in separate `*_skeleton.xml` files; animations in per-clip XMLs of per-frame, per-bone 4x4 matrices.
