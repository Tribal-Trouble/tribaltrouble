# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Cursor, Copilot, and friends)
working in this repository. Humans are welcome to read it too; it is a condensed version of
what a new contributor picks up in their first week.

Start with [README.md](README.md) for build and setup details, and
[docs/development-workflow.md](docs/development-workflow.md) for how work is branched and
shipped. This file covers the rules that are easy to get wrong.

## What this project is

Tribal Trouble is a 2004 realtime strategy game by Oddlabs, released under GPLv2 in 2014.
This fork brings it back online, keeps it buildable, modernizes the renderer, and ships it
on Steam. It is a live game with real players, a live matchmaking server, and a live
database. Changes that break wire compatibility or simulation determinism take the
multiplayer population down with them, so those two areas have hard rules below.

The codebase is old Java carried forward. It is not idiomatic modern Java everywhere, and
that is fine. Match the surrounding code rather than rewriting it in passing.

## Policy: creative work stays human

This project does not ship AI-generated creative content. Code is the exception, and even
there the bar is human review.

**Not allowed, in any form, generated or touched up by a model:**

- **Translations.** No machine or model output in the locale files. Translations are written
  and reviewed by human translators through the shared sheet.
- **Art.** Textures, models, icons, UI graphics, concept art, logos, store or marketing
  imagery. Art comes from the project's artists.
- **Sound.** Music, sound effects, voice, ambience.
- **Game writing** follows the same principle: unit and building text, campaign dialogue,
  tutorial copy, and other player-facing narrative are written by people.

This is not a formatting preference. It is a line about what the game is made of, and it
holds even when the result would be "good enough" or is "just a placeholder". Do not
generate an asset to unblock yourself, to demonstrate a feature, or to fill a gap while
waiting on a human. If a feature needs art, sound, or a string that does not exist yet, say
so and stop; use an existing asset or an obvious stand-in that nobody could mistake for
final, and flag it.

Mechanical transforms of artist-made art with the project's own tools are not generation:
splitting a mesh by bone or cropping a texture region with the Blender add-on, or running the
`assets` conversion tasks. Do those when asked, and say in the PR that you did.

**Code generated by an agent is allowed, and is a draft until a human reviews it.** Do not
merge it, push it, or describe it as finished on the strength of the model having written
it. Machine-readable and derived files (build output, generated sources, the geometry and
texture conversion the `assets` tasks perform) are not creative content and are unaffected.

Documentation, comments, commit messages, and PR descriptions written by an agent are fine.
They describe the work rather than being the work.

## Repository layout

| Path | What lives there |
|---|---|
| `common/` | Code shared by client and server: networking (`com.oddlabs.net`, the ARMI RPC layer), matchmaking and router wire interfaces, deterministic event log, geometry, utilities |
| `tt/` | The game client: rendering, GUI, input, audio, world simulation, models, pathfinding, campaign, Steam integration. `com.oddlabs.tt.Main` is the entry point |
| `server/` | The two server processes: matchmaker (`com.oddlabs.matchserver`) and router (`com.oddlabs.routerserver`), plus the Discord bot integration |
| `bugserver/` | The crash report service behind `bug.tribaltrouble.org`: stores each report with its event log and files it as a ticket. `deploy/` has the unit file and nginx config |
| `assets/` | Art source and the Gradle tasks that convert it into the binary geometry and texture formats the game loads |
| `tools/` | Offline converters: geometry, fonts, images |
| `servlet/` | Legacy web endpoints from the original Oddlabs deployment |
| `database/` | Numbered SQL migrations for the matchmaking database, plus rollbacks |
| `docs/` | Workflow, releasing, translations, event logs, save migration |
| `ci/` | CI support data (Spotless p2 formatter cache seed) |

All Java lives under `com.oddlabs.*`. `common`, `tt`, and `tools` are JPMS modules with a
`module-info.java`; adding a dependency may mean editing it.

## Build and run

The project targets **Java 26**. A lower JDK fails the build. If your default JDK is older,
point `JAVA_HOME` at a JDK 26 install for the Gradle invocation.

```bash
./gradlew tt:run              # run the game client
./gradlew :tt:compileJava     # fastest check that client code still compiles
./gradlew build               # build everything
./gradlew spotlessApply       # fix formatting
./gradlew spotlessCheck       # what CI gates on
./gradlew server:runMatchmaker
./gradlew server:runRouter
```

On Windows use `gradlew.bat`. Platform packaging tasks (`tt:packageWindows`,
`tt:packageLinux`, `tt:packageMacArm64`, `tt:packageMacX86`) only run on their matching host
OS.

Compiling proves the code builds. Running it is what catches the bugs. Never claim a change
works because it looks right. Two ways to run it without a person at the keyboard:

- **Headless simulation tests**: `./gradlew :tt:test` builds a world with no window, no GL and no
  audio and runs scenarios against it, single world and two peers in lockstep. Each scenario ends
  by asserting the world checksum, so any simulation change fails it. Re-baseline a stored
  checksum only in a commit that bumps `SIM_VERSION`, and only when the maintainer agreed to the
  change. New gameplay rules get a scenario here, in `tt/src/test/java/com/oddlabs/tt/headless/`.
- **Scripted play-testing**: start the game with `-Dcom.oddlabs.tt.input.port=7777` and drive it
  over a loopback socket with `tools/scripts/ttinput.py`: press buttons by label, read the GUI tree
  and the game state, fast-forward, take screenshots. [docs/llm-play-testing.md](docs/llm-play-testing.md)
  is the guide, including a local two-client multiplayer recipe. This is how UI, menu and rendering
  changes are verified. It needs a display, so it does not run on hosted CI.

The socket is off unless that property is set, so shipped builds do not change.

## Definition of done

Before reporting a change as finished:

1. `./gradlew :tt:compileJava` (or the affected module's `compileJava`) passes.
2. `./gradlew spotlessApply` has been run, so `spotlessCheck` in CI will pass.
3. Player-visible changes get a line under `## [Unreleased]` in [CHANGELOG.md](CHANGELOG.md),
   written for players, in English, following the rules at the top of that file.
4. Simulation changes come with a headless scenario, and `./gradlew :tt:test` passes.
5. Gameplay and UI changes are described honestly: say whether you played them through the
   scripted driver, ran only the headless tests, or did not run the game at all.

Do not say "done", "ready", or "working" for code that has not compiled.

## Hard rule: wire compatibility

`common/src/main/java/com/oddlabs/util/Compatibility.java` holds two version numbers and
they mean different things.

- **`API_VERSION`** is the client to server wire protocol. The server checks it with strict
  equality at login and rejects mismatched clients with "please update". Bumping it locks
  out every older client and requires a server rebuild and deploy from the bumped ref. Bump
  it when a matchmaking ARMI interface or a serialized class crossing that boundary changes
  incompatibly.
- **`SIM_VERSION`** is the client to client gameplay determinism version. Clients report it
  after connecting; the server lists every game with its host's value, the client dims the rows
  on another value and refuses to join them, and the server refuses spectating across values.
  Bump it when a change alters lockstep simulation behavior. It needs no server deploy and
  locks nobody out; players on different values see each other's games but cannot enter them.

CI has an `api-guard` job that fails if any of these files changed since the last
`API_VERSION` bump:

```
common/src/main/java/com/oddlabs/matchmaking/MatchmakingServerInterface.java
common/src/main/java/com/oddlabs/matchmaking/MatchmakingClientInterface.java
common/src/main/java/com/oddlabs/matchmaking/MatchmakingServerLoginInterface.java
common/src/main/java/com/oddlabs/router/RouterInterface.java
common/src/main/java/com/oddlabs/router/RouterClientInterface.java
common/src/main/java/com/oddlabs/router/GameInterface.java
common/src/main/java/com/oddlabs/registration/RegClientInterface.java
```

ARMI dispatches by method signature order, so renaming a method, reordering parameters, or
inserting a method into one of those interfaces is a breaking change even when it compiles
on both sides. If a change genuinely is wire compatible, that is a maintainer's call to
record with an empty `[api-compat-ack]` commit, not something an agent decides.

`common/src/main/java/com/oddlabs/bugreport/` is the JSON contract between the game's crash
handler and the bug server. It is not ARMI and not covered by `API_VERSION`, but the server is
deployed separately, so a field change there needs a bug server deploy before clients ship it.

**Never bump either version on your own initiative.** Point out that a bump looks necessary
and let the maintainer decide, because a bump has deployment and player-facing consequences
an agent cannot see.

## Hard rule: simulation determinism

Multiplayer is lockstep: every client runs the same simulation from the same inputs, and
only commands travel over the network. The same property makes `event.log` replay work (see
[docs/event-logs.md](docs/event-logs.md)). Any divergence between clients is a desync that
ends the game for everyone in it.

Simulation code is `tt/src/main/java/com/oddlabs/tt/` under `model/`, `model/behaviour/`,
`pathfinder/`, `landscape/`, `player/`, `trigger/`, and anything they call. In that code:

- Never read wall-clock time, `System.currentTimeMillis`, or frame rate. Simulation time
  comes from `LocalEventQueue` and `AnimationManager` ticks.
- Never introduce unseeded randomness. Simulation RNG is seeded deterministically (for
  example `new Random(42)` in `World`); leave the seeding alone.
- Never let iteration order depend on hashing. Prefer ordered collections and stable sorts.
- Never branch on anything local to one client: settings, resolution, input state, whether a
  sound played, Steam availability, locale.
- Do not rewrite existing float math in simulation paths, even to "optimize" it.

Rendering, GUI, audio, and camera code is not part of the simulation and is free of these
constraints. When a change straddles the line, keep the simulation side minimal and put the
presentation logic on the other side.

## Code style

Formatting is mechanical: Spotless with the Eclipse formatter configured from
`intellij-java-style.xml`. Run `./gradlew spotlessApply` and do not hand-format.

Beyond formatting, the house preferences are:

- **Minimal diffs.** Keep the original order of members when editing. Do not reformat,
  reorder, or modernize code you are not otherwise touching.
- **Comments are for constraints, not narration.** One sentence explaining a constraint or a
  non-obvious invariant, or no comment at all. Rationale belongs in the PR description or in
  `docs/`. Do not leave comments that restate the code, and do not reference roadmap phases,
  plan steps, or ticket numbers in source comments.
- **Named constants over magic numbers**, including sentinel values.
- **No delegating wrapper methods.** If a method only forwards to another, call the real one.
- **Prefer a constructor overload** to editing every call site when adding a parameter.
- **Feature flags default to off.** Work merged into `main` that is not ready to be seen
  ships behind a flag that is off. `Globals.SHIPS_ENABLED` gated ships this way until they
  were released.
- Null annotations are JSpecify; Error Prone and NullAway run on every compile, with a
  disabled-check list in the root `build.gradle.kts`. Do not add checks to that list to make
  your code compile.

## Branching, commits, and PRs

Read [docs/development-workflow.md](docs/development-workflow.md) for the full model. The
parts agents get wrong:

- **Branch off `main` and merge back into `main`.** Not off `release`, not off a tag.
- **Never let a feature branch track `main` or any upstream branch.** Push with an explicit
  refspec when the time comes.
- **Do not push branches, open pull requests, or comment on issues unless explicitly asked
  to.** Committing locally is fine; anything that leaves the machine is the maintainer's
  call.
- **Small atomic commits** with short single-line messages in the imperative mood. No body
  unless it genuinely adds something.
- **The agent is never a committer or author.** Commits are authored by the person running
  the agent, under their git identity. Do not add `Co-Authored-By` lines for the agent,
  generated-by footers, or session links to commits or PR bodies, and do not change
  `user.name` or `user.email` to name a model.
- `hotfix/*` branches off `release`, merges to `release`, then forwards into `main`.

## Translations

Game strings are `.properties` bundles under `tt/src/main/resources/com/oddlabs/tt/`, with
`X.properties` as the English base and `X_<locale>.properties` per language.

- **Never write a translation into a locale file.** Not a guess, not a "rough draft", not a
  correction to one that reads wrong. Translations come from the shared Google Sheet and are
  reviewed by human translators; see
  [docs/translations/README.md](docs/translations/README.md). This is the
  [creative work policy](#policy-creative-work-stays-human) in practice.
- A new string means adding the key to the **English base file only**. The sync workflow
  gets it in front of translators.
- Do not reorder or reformat locale files; the sync owns their key order.
- Do not hand-edit `tt/translations-baseline.csv`.

## Assets

Binary art, geometry, textures, and audio live in this repository and stay here. Do not
upload game assets to external services, mirrors, or scratch repositories, and ask before
touching third-party asset repos. Regenerate derived assets with `assets:geometry` and
`assets:textures` rather than committing hand-built binaries.

Art and sound are authored by people. Never generate a texture, model, icon, or sound to add
to the game, and never run an existing asset through a model to upscale, restyle, denoise,
or "clean it up". See the [creative work policy](#policy-creative-work-stays-human).

## Database

`database/` holds numbered forward migrations with matching rollbacks. Add a new numbered
file rather than editing one that has already been applied, and remember that the live
database is migrated by hand, so a merged migration is not a deployed migration.

## Quick sanity list

- Did anything under `common/.../matchmaking`, `router`, or `registration` change? Check the
  wire rules.
- Did anything under `tt/.../model`, `behaviour`, `pathfinder`, `landscape`, or `player`
  change? Check the determinism rules.
- Did a user-visible string change? English base file only, and no translations from you.
- Does the change want art, sound, or narrative text? A person makes that, not you.
- Did you run `spotlessApply` and a `compileJava`?
